# AGENTS.md

WhatsApp bot (Node.js/Express, ESM) with **two flows**: the **main agent** that sells the studio's services (WhatsApp agents, web apps, web pages) and the **útiles escolares** sales flow ("útiles escolares") from `UtilesEscolares.xlsx`, which now runs as an **on-demand demo**. User-facing replies and console logs are in Spanish.

> Histórico: el repo alojaba además un flujo de consulta de equipos (laptops, `Laptops.xlsx` + `lib/search.js`) con usuarios autorizados. Ese flujo fue eliminado por completo.

## Main agent (SERVICIOS) + demo de útiles

- **Every session starts at state `SERVICIOS`**: the first message (and any later message in that state) goes through `handleServicios` in `lib/store.js`. Reply = `SERVICIOS_REPLY` "¿Quieres ver una DEMO de un agente de ventas de útiles escolares? 1. Ver una DEMO de un agente de ventas 2. Comunicarme con Evelyn 3. Solicitar una APP, Página web o Chatbot para tu negocio".
- **AI-driven**: with `GEMINI_API_KEY`, `handleServicios` calls `ai.askGeminiServices(ai.buildServicesSystem(), session.serviciosHistory)` (`lib/ai.js`); Gemini replies in Spanish and may set JSON flags: `ir_demo` (enter demo), `formulario` (enter the requirements form), `evelyn`, `despedirse`, `requerimientos`. Without a key, rule fallbacks apply: `^3$` → Evelyn, `^2$`/`isServiceRequest`/`isChatbotRequest` → start the requirements form, `isDemoRequest` → demo, anything else → re-send `SERVICIOS_REPLY`. The `SERVICIOS` state ignores images/documents (`SERVICIOS_SOLO_TEXTO`). Requires `GEMINI_API_KEY` to override `CHATBOT_FIELDS.reply` (params) unless state is `SERVICIOS`.
- **Demo**: the demo request (`isDemoRequest`, words like `demo`, `muestra`, `prueba`, `ver` + `agente`) calls `startDemo(from, session)` — sets `session.demoMode = true`, sends `DEMO_INTRO` then the útil greeting (`SALUDO`). The full útiles state machine runs **only inside demoMode**; in production a fresh session with no demo starts at `SERVICIOS`. When the demo session is created it is treated like a real buyer (greeting `SALUDO`, catalog, chats). Leaving the demo: the word `exitDemo` — or the **terminal closures of the demo** (sale finished, queda validated, despedida, Evelyn via option 2/"Evelyn", chatbot requirements approved, `IA` `despedirse`/`pedido_finalizado`) — call `maybeClose(from, session)`: if `demoMode` → `exitDemo` ("Salgo de la demo..." → `SERVICIOS_REPLY`, keeps `serviciosHistory`); else → `deactivate`.
- **Form**: `CHATBOT_FIELDS` now has **9 fields** starting with `servicio` ("¿Qué tipo de servicio deseas? 1. Agente de WhatsApp 2. App web 3. Página web") followed by the original 8 (negocio, productos, canales, tareas, volumen, catálogo, idioma/integraciones, contacto); `CHATBOT_INTRO`/`CHATBOT_APROBADO` are service-neutral ("un servicio digital").
- **Logs**: approved requirements log line is `REQUERIMIENTOS SERVICIO de <nombre>: ...`.

## AI (optional) — Google Gemini free tier
The útiles flow has an **optional AI mode**: if `GEMINI_API_KEY` is set (`lib/ai.js`, no new deps, uses global `fetch`), the greeting's option **1** (and any free text / photo / document from the saludo) enters state `IA_CHAT` — a free-form dialogue driven by `gemini-3.1-flash-lite` (`GEMINI_MODEL` env). Model output is **structured JSON** (`askGemini` in `lib/ai.js`, `responseMimeType: application/json` + `responseSchema`): `reply`, `carrito[{producto,cantidad}]`, `entrega{direccion,diaHora,nombre,genero,domicilio}`, `pedido_finalizado`, `despedirse`, `enviar_catalogo`. **The bot never trusts Gemini for prices**: every `carrito` entry is re-validated against the catalog via `findItems` before entering `seleccion`; the final quote image is always built by `buildPriceImage` from catalog data. **List-driven quotes**: when the client sends a list of útiles (text/photo/document) Gemini builds the quick carrito and marks `recibir_lista` → the bot first sends the fixed message "He recibido tu lista de útiles y ya te estoy preparando la cotización inicial con los productos que tenemos disponibles. Espera un momento por favor", then the **quick cotización** (5-column image `Cantidad | Descripción solicitada | Producto | Valor unitario | Valor total`), and only then Gemini's reply, which starts the review of the products **NO disponibles** of the initial cotización one question at a time (the fixed message and its image are sent together, only once per list — dedup by cart signature; the reply is sent ~2 seconds after the image — `IA_IMAGEN_REPLY_DELAY_MS` env, default `2000` — so WhatsApp doesn't reorder them, and the same delay applies after the final cotización image; the reply must begin directly with the first no-disponible question, without re-greeting or re-announcing the list/cotización, which the prompt forbids explicitly). For **multi-line text or document lists** the quick cotización is **seeded verbatim** from the parsed list (`matchListLines(listLines, products, { includeAll: true })` + `seedSeleccionFromItems` in `handleIa`): one row per solicited line, "Descripción solicitada" = the client's exact text **including the quantity**, and qty = the line's leading number (default 1) — products are **never grouped** (`1 masking grueso` ≠ `1 masking delgado`) nor quantities modified; matched lines get catalog pricing via `findItems`, unmatched ones render as "no disponible" $0.00. This seed overrides Gemini's `carrito` for the initial image; single-line texts and photos keep using Gemini's `carrito` via `applyIaCarrito`, which keys rows by `linea` (`prod|${linea}`, so distinct solicited lines stay separate). `matchListLines` gained the `includeAll` option (keeps keyword-less lines like "masking") used only by the AI seeding; the non-AI flow still drops them. Gemini (prompt rule MISMO PRODUCTO, backed by `findItems`) recognizes when the solicited product **is the same** catalog product with a slightly different wording (e.g. "1 Cuaderno universitario de 100 hojas a cuadros" ≈ "Cuaderno universitario cuadros 100 hojas marca zien") and adds it directly without asking; only genuinely missing products are reviewed as "no disponible". The options question is natural and flexible (not a rigid template): it opens with the solicited line — `En la lista de útiles que me enviaste pide: X, tengo disponible: ...` (first item), `Ok, en la lista pide: X, tengo disponible: ...` (following items), and `Ya lo agregué` after the client picks one — each option on its own line and the final question on its own line. Gemini must analyze the **function** of each requested product and offer only catalog products that fulfill the same function (never a different one, e.g. no compass for a "calculadora científica"), may explain naturally why it's offering a product when the client asks, and skips silently (with **no message at all** — the prompt forbids any fixed phrase like "no lo tengo disponible", "no tengo un producto que cumpla esa función" or "¿Deseas continuar con el siguiente ítem?") any solicited item with no same-function option. The AI system prompt's `PEDIDO ACTUAL` section renders each no-disponible item with its original solicited text (e.g. `1 x no disponible (solicitado: "escoba")`) so Gemini can identify and resolve every missing product without relying on memory. Gemini resolves the list **one question per message** (only products with 2+ options are asked; single-option products are auto-added silently; a solicited item with no catalog option that fulfills the same use stays as `no disponible` $0.00 **without sending any message about it** — the bot skips it silently (it's already shown in the image) and moves to the next no-disponible item), then says "eso es todo lo que tengo disponible de la lista que me enviaste", offers mochilas/cartucheras/loncheras, and only marks `pedido_finalizado` once the client confirms no more additions (→ final cotización + close). The 5-column image is used **only** when a list was received (`session.listaMode`); otherwise `buildPriceImage` keeps the `Cantidad | Producto | Precio` layout. The list cotización always includes **every** requested item: catalog matches get priced rows and solicited items with no catalog match appear as "no disponible" (gray) with $0.00 unit/total (via `addNoDisponible` in `lib/store.js` for the non-AI `unavailable` step and for `carrito` entries that `findItems` can't match, plus a safety net in `handleIa` that re-parses the raw list text/document and adds any `precio == null` items Gemini omitted). The **final cotización** (the one sent with the order-confirmation message) is always built from a snapshot of the quick list cotización (`session.listaBase`, captured in `handleIa` when `recibir_lista`): `mergeListaRows` (exported from `lib/store.js`) keeps every original "Descripción solicitada" line intact and only swaps the Producto/precio/qty of the items the client actually selected during one-by-one resolution (matching by catalog key or solicited line); products the client didn't touch stay exactly as in the quick cotización, and any newly added items are appended. When `pedido_finalizado` is true the bot renders the final image **before** Gemini's confirmation reply and asks for an explicit confirmation (`IA_CONFIRMA_PEDIDO`, "¿Confirmas tu pedido?"); the user's `sí`/`confirmo`/`de acuerdo`/`1` then triggers a short payment text with the exact 50% amount (`PAYMENT_IA`, e.g. "transfiere el anticipo del 50%: $12.50") and moves to `ESPERA_COMPROBANTE`; any other reply returns to `IA_CHAT` (Gemini adjusts the order). The 50% is computed over the total **including the delivery surcharge** when the client chose `domicilio` (fixed `DOMICILIO_RECARGO` env, default `3`, e.g. "$3.00"; also rendered as a "Recargo por entrega a domicilio" row in the final image). In `ESPERA_COMPROBANTE` the receipt is **verified with Gemini vision** (`askGeminiReceipt` in `lib/ai.js`): it first checks the image is really a payment comprobante (`es_comprobante`), extracts monto/titular/fecha and checks that the amount is ≥ the 50% anticipo, the holder is "Evelyn Lizeth Zambrano" and the comprobante date is **today** (America/Guayaquil) → if OK replies `COMPROBANTE_OK_IA` (thanks + closes the session); if not, replies a kind, **varied** message (`COMPROBANTE_MAL_VARIANTS`, cycled by `session.receiptAttempts`, third attempt offers an asesor) with the motivo and stays waiting. Re-sending the **same image** gets `COMPROBANTE_MISMA_IMAGEN` instead of a repeated review. If AI is off or fails, it falls back to the manual `COMPROBANTE_MANUAL` path (operator logs the expected 50% and today's date). Menu options 2/3 (Evelyn / chatbot para tu negocio) and the entire rule state machine are untouched when AI is on; **without a key the bot behaves exactly as before** (all tests pass). On API errors/quota (429) `askGemini` returns `null` → reply `AI_FALLBACK` and the session stays in `IA_CHAT` (never breaks). Photos sent in `IA_CHAT` are downloaded (`server.js normalizeInbound`, only when `isAiEnabled()`) and sent to Gemini inline as base64 (free vision). Conversation history lives in `session.iaHistory` (last ~24 turns).

> Model note: Google retired the 2.x models for new API keys (404). Use a current free model — `gemini-3.1-flash-lite` (default), `gemini-3.5-flash`, or `gemini-3.6-flash` — via `GEMINI_MODEL`. The `generateContent` endpoint is still supported (legacy); the newer Interactions API is not used here.

### Hybrid-model hardening (rule + IA coherence)
- **Seed sin depender de la bandera**: a multi-line text or document list is seeded verbatim (`matchListLines` + `seedSeleccionFromItems`) and gets the `PROCESANDO_LISTA_IA` message + quick image whenever `recibir_lista` **or** the message is a list (`isListMessage`), so a missed `recibir_lista` never drops the image. The initial cotización always includes **every** list item (even no-catalog matches, shown as "no disponible" $0.00 with the client's exact text); photos aren't re-parsed, so the prompt forces Gemini's `carrito` to include every visible item (unmatched → "no disponible").
- **Carrito por fusión** (`applyIaCarrito`): instead of replacing `seleccion`, it merges — rows Gemini omits are preserved (safety net), `cantidad: 0` removes a row, and a matched/unmatched upsert supersedes the previous row for the same solicited line (keys unified to `prod|${linea}` / `no disponible|${linea}`; repeated identical lines get a `#2` suffix so they stay **two separate rows**, never summed). Only single-line texts/photos keep using Gemini's `carrito` directly.
- **`mergeListaRows` tolerante**: besides matching by catalog name or exact `linea`, it now matches by `linea` stripped of its leading quantity, so "1 masking grueso" ≡ "masking grueso".
- **Cierre unificado**: only `pedido_finalizado` closes (confirm → 50% → `ESPERA_COMPROBANTE`). `enviar_cotizacion` is sent **only** when the client explicitly asks for the quote and — if any delivery data exists (`direccion`/`nombreEntrega`/`diaHora`/`genero`/`delivery`) — reuses the **final** layout (ENTREGA block + `DOMICILIO_RECARGO`), deduped against `finalSig`. `isCatalogRequest` no longer intercepts `IA_CONFIRMA_PEDIDO` (the AI handles "catálogo" there). Re-sending the **same** list (`session.lastListSig`) no longer reverts the cart.
- **Intents en modo IA**: `isQuoteRequest`, `isPayAllOnPickup`, `isPaymentRequest` and `isPhotoRequest` now work in rule states even with AI enabled (the catalog word still goes to `NUMEROS`, by design).
- **Imágenes y orden**: AI quote images (`sendCotizacionIa`/`sendFinalCotizacionIa`) now render `session.headers`; rule-flow preliminary/final images (`sendPreliminaryCotizacion`/`sendFinalCotizacion`) also wait `iaImageReplyDelay()` before the text; `enviar_catalogo`/`enviar_foto` images are sent **before** the reply text so WhatsApp doesn't reorder them.
- **Género ampliado**: `handleGenero`/prompt now accept `niña`, `niño`, `adolescente`, `adolescente hombre`, `adolescente mujer`, `hombre`, `mujer`, `adulto` (typo "adolecte hombreo o mujer" fixed).
- **CONFIRMACIÓN**: the final-quote confirmation message is now "Te envío la cotización de lo solicitado. Revísalo y cuéntame si estás de acuerdo?" (ends in `?`, so `IA_CONFIRMA_PEDIDO_MSG` is not appended).

## Commands
- `npm start` runs the server.
- `npm test` runs `node --test test-usability.mjs` (unit/usability tests, read-only). There is no lint/typecheck setup.

## Excel quirks (easy to miss)
- `UtilesEscolares.xlsx` (slim copy, no photos): sheet `Hoja1`, header row **1** = `Producto | Descripcion | Precio de venta al publico ` (trailing space + NBSP possible — `normalize()` handles it). Rows 2+ are the 59 products (the catalog grows as rows are added). The price header contains a non-breaking space and trailing space; `normalize()` in `lib/excel.js` (lowercase + strip accents + trim + NBSP→space) is what makes the alias `'precio de venta al publico'` match in `lib/utiles.js`.
- **Product photos**: drop images into `imagenes/` named `<Número de producto>.<ext>` (e.g. `1.jpg`, `12.png`; `.jpg/.jpeg/.png/.webp`). `findProductImage()` in `lib/utiles.js` resolves them (dir overridable via `UTILES_IMAGES_DIR` env). When the AI chat asks for a photo of a product that has an image, Gemini marks `enviar_foto` with the product number and the bot sends that file via `sendProductPhoto()` (no photo → message "no tengo una foto disponible" + catalog link). The build of the AI system prompt lists exactly which products have photos, so Gemini never claims a photo exists that isn't in the folder.
- All matching/text goes through `normalize()` in `lib/excel.js` (lowercase + strip accents). `normalize()` also converts `\u00a0`→space and trims.

## Gotchas
- `server.js` caches the workbook for the process lifetime (cache key = `UTILES_PATH`). Edits to the `.xlsx` require restarting the server; in production (Render) that means pushing the updated file to GitHub `main` → auto-redeploy. The YCloud webhook URL never changes. The útil store loads the catalog **lazily** (`ensureProducts()` in `lib/store.js`): the greeting and option 2/`no`/`asesor` never fetch it — it's loaded into memory on the first action that needs it (option 1, option 3, a product query or a confirmed document) and stays cached for the process.
- **Production runs on Render** (`pc-venta-ia.onrender.com`). Env vars live in the Render dashboard (`YCLOUD_API_KEY`, `YCLOUD_PHONE`, `YCLOUD_WEBHOOK_SECRET`, `GEMINI_API_KEY`, `DOMICILIO_RECARGO`), not in `.env`. The repo is private; `.env` and `node_modules` must never be committed.
- Without `PHONE_NUMBER_ID`/`ACCESS_TOKEN` in `.env`, replies are only logged to console (dev mode). `.env` is gitignored; copy `.env.example`. Signature verification (Meta `x-hub-signature-256` and YCloud `ycloud-signature`) is skipped only when the corresponding secret is empty; when a secret is set, a request missing its signature header is rejected with `401`.
- **Webhook routing** (`server.js`): **everything routes to `utilesStore.handleMessage`** (which starts sessions in the `SERVICIOS` main agent and runs the útil demo only inside `demoMode`). There is no authorization, no laptop session, and no activation keyword — every inbound message (text or media) from anyone goes to `handleMessage`. `res.sendStatus(200)` is sent before processing, so YCloud/Meta won't retry.
- **Per-sender serialization**: `runSerialized(from, fn)` in `server.js` queues message processing per `from` so the in-memory per-sender state machine never races when a user sends several messages quickly.
- **Útiles flow** (`lib/store.js`): a state machine per `from` with states `SERVICIOS → (SALUDO | CHATBOT)`, then `SALUDO → (IA_CHAT | CHATBOT | ESPERA_LISTA) | IA_CHAT → IA_CONFIRMA_PEDIDO | CHATBOT → CHATBOT_CONFIRMA → CHATBOT_EDITAR | SELECCION → CANTIDAD → AGREGADO → (SUGERENCIA → CONFIRMA_SUGERENCIA → MODELO_MOCHILA) → CONFIRMA_COTIZACION → GENERO | ESPERA_LISTA/CONFIRMA_ARCHIVO → RESOLVER_LISTA (item por item) → AGREGADO → ... | CONFIRMA_ARCHIVO → PREGUNTA_PRODUCTO → PREGUNTA_DISPONIBLE → ENTREGA → UBICACION → DIA_HORA → NOMBRE_ENTREGA → CONFIRMA_PEDIDO → ESPERA_COMPROBANTE | MODIFICAR → (AGREGADO | RETIRAR)` (plus `DESACTIVADO`, only reachable in production when no demo is active). The **first message** of a session goes to `handleServicios` (state `SERVICIOS`, see the main agent section at the top); inside the demo the greeting shows options `1` (cotización), `2`/`no` → Evelyn, `3` (chatbot para tu negocio) — **no catalog option in the greeting** (the catalog is shown on request by word via `isCatalogRequest`, e.g. "catálogo"/"qué tienes", or after option 1 via `PREGUNTA_DISPONIBLE`). `2`/`no` → reply "Ok, de aquí en adelante Evelyn chateará contigo." and close via `maybeClose`: in the demo it **returns to `SERVICIOS`** (main menu); in production → `DESACTIVADO` (the bot never replies again for that `from` until the process restarts, so Evelyn continues the conversation manually from WhatsApp Business); a free-text request to talk to Evelyn (matched by `isTalkToEvelyn`, e.g. "necesito comunicarme con Evelyn", checked in `handleMessage` before any other intent/state, so it works in every state and both AI/non-AI) does the same. Option `3` (or any text with the word `chatbot`/`bot inteligente` via `isChatbotRequest`, from any state) → `CHATBOT`: a **9-question** requirements form (`CHATBOT_FIELDS`: `servicio` first — "¿Qué tipo de servicio deseas? 1. Agente de WhatsApp 2. App web 3. Página web" — then negocio, productos, canales, tareas, volumen, catálogo, integraciones/idioma, contacto) storing answers in `session.chatbotInfo`; after the last answer it sends a summary (`buildChatbotSummary`) + approval ask → `CHATBOT_CONFIRMA`; `sí` logs the requirements for the operator (line `REQUERIMIENTOS SERVICIO de ...`) and replies that an asesor will contact the client personally (via `maybeClose`; in the demo it returns to `SERVICIOS`); any other reply → `CHATBOT_EDITAR` (numbered field list → pick a number → enter the new value → updated summary → back to `CHATBOT_CONFIRMA`; "listo" returns to the summary). Media in the chatbot states replies `CHATBOT_SOLO_TEXTO` and stays in state. Multi-line text lists are matched directly; **PDF/Excel documents first ask `CONFIRMA_ARCHIVO` ("Recibí tu archivo. ¿Genero la cotización con esa lista?")** (buffer kept in `session.pendingFile`), and on `sí` set `session.busy = true` while parsing (`parseFile`, try/catch → `FILE_UNREADABLE` on failure) + building the image, cleared in `finally` (`isBusy(from)` is exposed for the webhook, which replies `ESPERA_GENERANDO` immediately to any message arriving while busy; `completar el pedido`/`detener` in `CONFIRMA_COTIZACION` jumps straight to `MODIFICAR`). `CONFIRMA_COTIZACION` asks "¿Estás de acuerdo con la cotización? Si deseas ajustar algo, dime qué producto agregar o quitar."; `no`/`modificar`/`2` (or any other reply) → `AGREGADO` (modify); `1`/`sí`/`de acuerdo` → `GENERO` ("¿Tu lista de útiles es para niña o para niño? Dime cuál.", stores `session.genero` rendered as "Para: X" in the final cotización image, re-asks on invalid) → `ENTREGA`. On `no` → `PREGUNTA_PRODUCTO` ("¿Deseas preguntar por un producto específico?"), and its `no` → `PREGUNTA_DISPONIBLE` ("¿Deseas ver lo que tengo disponible?") → `sí` sends the full catalog (producto, descripción y precio, via `catalogoText()`) and goes to `ESPERA_LISTA`; its `no` → farewell + closes. Asking "qué tienes"/"catálogo"/"qué hay" (matched by `isCatalogRequest`, checked before the payment/photo intents, any state except `ESPERA_COMPROBANTE`) sends the same catalog text and keeps the current state. When offering mochilas/cartucheras/loncheras (`SUGERENCIA`/`CONFIRMA_SUGERENCIA`) the replies append the WhatsApp catalog link `https://wa.me/c/593987695938`. After `UBICACION` (dirección) and `DIA_HORA` (día/horario), `NOMBRE_ENTREGA` asks "¿A nombre de quién realizamos la entrega?" and stores `session.nombreEntrega`, which is rendered as "A nombre de: X" in the final cotización image. Lines are classified by `matchListLines()` (`lib/utiles.js`) into 4 buckets (a line that is only a quantity continuation — `unidades)`, `pcs)`, `)` — following a line ending in a digit is merged into it first, so `1 caja de pinturas triangulares gigantes 12` + `unidades)` become one item), and a line **starting with `para`** is merged into the previous line (continuation, so `cartuchera` + `para niña` → one priced item); an orphan `para` fragment (no previous line) is dropped in `matchListLines` and in `handleEsperaLista` a lone message starting with `para` → `PIDE_LISTA`, checked in order: **header** (text with `grado|curso|paralelo|escuela|colegio|unidad educativa` only — no "lista de útiles"/"nombre del estudiante"/"año lectivo" — → rendered at the top of the image, also stored in `session.headers` for the preliminary/final images), **footer** (`fecha|entrega|firma|docente|profesor|maestro|nota|observacion|adicional|por favor|agradec|gracias|atentamente|importante|recordar|presentar|presente lista|inicio de clases|debe|deber` → dropped, never shown), **omit** (`libro|libros|novela|uniforme|dirección|domicilio|calle|avenida|cdla|urbanización|ciudadela|referencia|teléfono|celular|correo|email|whatsapp` → dropped, never shown), and **product** (verificación de pertenencia: a line is quoted only if it belongs to útiles escolares/limpieza. `findItems` matches per-word with **IDF weighting** (rare tokens like `triangular` outrank generic ones like `caja`, so `caja de pinturas triangulares` → *Caja de Esfero Triangular Bester* (a real catalog product) and NOT *Caja de 12 lápices*; `pinturas jumbo` → *Pintura Jumbo Triangulare*; `caja de 12 lapices` still → *Caja de 12 lápices*) and singular/plural-aware (`pinturas`↔`pintura`, `triangulares`↔`triangulare`); it requires ≥1 token in the product **name** (description-only matches are discarded → `regla de 30 cm` picks *Regla Bester de 30 cm*, not *Juego Geométrico*; `escuadra`→no match). Name match → priced row quoting the **client's original line text** as `linea` and the catalog name as `catalogo` (both stored in `seleccion` when a list is processed; the list-driven image renders them in separate columns "Descripción solicitada" and "Producto"); no name match but a `UTILES_ITEM_RE`/`LIMPIEZA_ITEM_RE` keyword (`cuaderno, lapiz, goma, regla, tijera, mochila, cartuchera, escoba, jabon, cloro, cepillo dental, papel higienico, archivador, mandil, rompecabezas, vaso, pelota...`) → row "No disponible" (belongs but not in catalog, original text shown); neither → the line is **dropped** (never quoted, e.g. `xyzfoo`). Only priced items enter `seleccion`; a `unavailable` step also adds its line to `seleccion` as a "no disponible" row (`addNoDisponible`, `precio: null`) so the list cotización image shows every requested item, with $0.00 for the ones not in catalog). Item rows keep the **document line order** (no reordering). Items are matched against `Producto`+`Descripcion` via `findItems()` (`lib/utiles.js`, token scoring, top 5, **min token length 3**, measure words `unidad|unidades|unids|pcs` are stopwords so a stray `unidades)` is never priced) → they populate the session's `seleccion` map and a preliminary PNG price image is built with `buildPriceImage()` (sharp) with the **5-column list layout** (`session.listaMode`) → asks "¿Es esta la cotización que deseas? 1/2". `2` → `MODIFICAR` (add or remove products). `1` → `ENTREGA` (delivery only) → `UBICACION` stores `session.direccion` → `DIA_HORA` stores `session.diaHora` → final cotización image rendered with an ENTREGA block (`buildPriceImage(rows, { entrega, recargo })`, `recargo` = `DOMICILIO_RECARGO` when the client chose `domicilio`, rendered as a "Recargo por entrega a domicilio" row and included in the TOTAL) + 3-option menu (1. Realizar el pedido / 2. Deseo modificarlo / 3. No estoy interesado). Option 1 → `ESPERA_COMPROBANTE`: instructs to transfer the 50% (non-refundable, computed over the total **including** the delivery recargo when applicable) **indicating the exact amount** + the rest on delivery and attach the receipt; **the receipt is not OCR'd — verification is manual**: any image/document while in `ESPERA_COMPROBANTE` is treated as the comprobante, logs the customer, order total and expected 50% for the operator, replies "Recibimos tu comprobante... Verificaremos que el anticipo del 50% ($X)... a nombre de Evelyn Lizeth Zambrano con fecha de hoy" and closes the session (text in that state re-asks for the receipt). Option 3 → cordial farewell and closes. A single product query shows price and asks quantity (`CANTIDAD`), stored in `seleccion`. Session fields: `direccion`, `diaHora`, `nombreEntrega`, `genero`, `sugerido` (once suggested, mochilas/cartucheras/loncheras are offered at most once per shopping round), `pendingFile` (document buffer awaiting confirmation), `busy` (generation in progress). In `ESPERA_LISTA`, messages mentioning a sent file (`pdf|archivo|documento|adjunt|envie|mande|mando|reenviar|subi|recibi|ya te`) → `ARCHIVO_NO_RECIBIDO` (stays in state); question/complaint wording (`de donde|donde|por que|porque|para que|de que|que es|como`) → re-send `PIDE_LISTA`; zero product hits → `PIDE_LISTA` (not `NO_ENCONTRADO`). `pago`/`transferencia` → payment instructions; `foto`/`imagen`/`catalogo` → "en nuestro catálogo..." (stays in state); photos are never OCR'd. Idle timers: 5 min → follow-up ("¿Sigues ahí?") only if the sale is not concluded, 14 min → "El chat se cerrará por falta de respuesta." and the session closes; if the sale already concluded (state `ESPERA_CONFIRMACION_RECIBO` or `PICKUP_AGENDA`) no idle message is sent — the session is dropped silently.
- **YCloud adapter** (`server.js`): if `YCLOUD_API_KEY` is set, text sends via `POST https://api.ycloud.com/v2/whatsapp/messages` with `X-API-Key`, body `{ from, to, type: "text", text: { body } }` (E.164 with `+`). `from` uses `YCLOUD_PHONE` or falls back to the inbound message's `to`. Images: upload `POST https://api.ycloud.com/v2/whatsapp/media/{phone}/upload` (multipart field `file`, E.164 with `+`, response `{ id }`), then send `{ type: "image", image: { id } }`. Incoming media (YCloud: `image.link`/`document.link` URLs; Meta: media ids resolved via Graph API) is downloaded by `downloadMedia()`. Incoming events are `whatsapp.inbound_message.received` under `event.whatsappInboundMessage` (`from`, `to`, `text.body`, `image`/`document`); both YCloud and Meta (`entry[].changes[]`) payloads are parsed by `toMessages()`. Signature header `YCloud-Signature` (`t=<ts>,s=<hex>` over `<ts>.<rawBody>`, HMAC-SHA256 with `YCLOUD_WEBHOOK_SECRET`) is verified when that secret is set. Otherwise the Graph API path is used (requires `PHONE_NUMBER_ID`/`ACCESS_TOKEN`).
